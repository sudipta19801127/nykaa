## 1. System Risk Classification

Under the standard three-tier governance scheme (**Low:** summarization/transcription; **Medium:** code generation/customer support tickets; **High:** medical data, hiring decisions, financial underwriting), the **Nykaa Domain Support Agent is classified as a MEDIUM-RISK AI system**[cite: 1].

### One-Paragraph Risk Justification
The Nykaa Domain Support Agent directly influences customer transactions, return authorizations, and logistical escalations by interpreting retail policies and accessing transactional order records (`check_order_status`)[cite: 1]. While it does not process high-risk automated actions—such as dispensing prescription pharmaceutical advice, deciding consumer credit lines, or handling unmasked financial accounts—an undetected failure or hallucination can cause real operational disruption[cite: 1]. Specifically, incorrect policy assertions regarding return windows, cash-on-delivery timelines, or reverse-pickup eligibility could lead to financial leakage (unwarranted merchant refunds) or customer dissatisfaction[cite: 1]. Consequently, the system operates above the Low-Risk threshold (passive summarization) but well below High-Risk critical tiers, firmly placing it in the **Medium-Risk category** where multi-agent verification, input/output guardrails, and deterministic reviews are required[cite: 1].

## 3. Application Layer Guard: Principle of Least Autonomy

### Architectural Guard Explanation
To limit the blast radius of potential agent tool manipulation or jailbreaks, the system enforces the **Principle of Least Autonomy**[cite: 1]:

1. **Isolation of Data Access:** Order lookup logic (`check_order_status`) is bound exclusively to the `Order Status Auditor` agent[cite: 1].
2. **Read-Only RAG Access:** The `Policy Retrieval Specialist` is strictly limited to vector index queries via `rag_lookup`[cite: 1].
3. **Zero-Tool Response Composer:** The `Customer Support Composer` is designed as a pure synthesis agent with zero tool bindings, preventing it from initiating unexpected side effects or unauthorized downstream queries[cite: 1].
4. **Programmatic Enforcement:** If an engineer or pipeline dynamically binds `check_order_status` to any agent other than the authorized auditor, `validate_agent_tool_bindings()` throws a `ToolAuthorizationError` and halts startup[cite: 1].

## 4. Empirical Escalation Threshold Justification

In `crew/tools.py`, the escalation score is computed continuously as[cite: 1]:
$$\text{escalation\_score} = 0.60 \times \text{delayed\_shipment} + 0.40 \times \left(\frac{\text{days\_since\_created}}{30}\right)$$

* **Escalation Cutoff ($\ge 0.70$):** In the deterministic dataset generated by `data/dataset.py`, orders with `days_since_created > 24` represent the **80th percentile of order age** ($24 / 30 \times 0.40 = 0.32$).
* An order is flagged for human escalation (`recommend_escalation = True`) if either:
  1. A shipment is actively delayed (`0.60`) and is more than $7.5$ days old ($0.60 + 0.10 = 0.70$).
  2. A non-delayed shipment reaches extreme aging beyond the 80th percentile ($> 24$ days).
